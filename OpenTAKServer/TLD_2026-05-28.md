## 1. Purpose

This document describes the high-level technical design of **OpenTAKServer (OTS)**, an open-source TAK server (Team Awareness Kit) compatible with ATAK, iTAK, WinTAK, TAKAware, TAKX, CloudTAK and PyTAK. The document is intended for architects, programme managers and technical leads who need insight into the structure, design decisions and coherence of the system.

OpenTAKServer's goal is to provide an easy-to-install, fully functional TAK server that runs on both servers and single-board computers (e.g. Raspberry Pi).

## 2. Scope

**In scope:**
- System architecture of OpenTAKServer

- Video streaming integration
- Plugin architecture

**Out of scope:**
- Internal workings of TAK client applications (ATAK, WinTAK, iTAK)
- Federation coupling (planned, not yet implemented)
- Installation and operational guides

## 5. Architecture Overview

OpenTAKServer is a Python application built on the **Flask** web framework, with **gevent** for asynchronous I/O. The server forms the core of a TAK ecosystem and handles communication between field devices.

### 5.2 Core Components

| Component | Description |
|---|---|
| **EUD Handler** | Handles TCP/SSL/UDP connections from TAK clients. Receives CoT messages and forwards them via RabbitMQ. |
| **Marti API** | Implements the TAK Marti protocol: certificate enrollment, contacts, CoT, data packages, group management, Mission API. |
| **OTS API** | REST API for the WebUI and external integrations. |
| **SocketIO** | Real-time WebSocket communication for the live map in the WebUI. |
| **RabbitMQ** | Message broker that distributes CoT messages between components via exchanges and queues. |
| **PostgreSQL** | Relational database for persistent storage (users, CoT history, missions, etc.). |
| **Certificate Authority** | Internal CA for creating and managing client certificates for TLS authentication. |
| **APScheduler** | Background tasks: fetching ADS-B data, AIS data, data cleanup, deleting video recordings. |
| **MediaMTX** | External video server for RTSP/RTMP/HLS streaming, managed via the OTS API. |
| **Plugin Manager** | Loads and manages optional plugins that extend core functionality. |

## 6. Design Decisions

| Decision | Rationale | Alternative Considered |
|---|---|---|
| Python + Flask as framework | Broad ecosystem, rapid development, good TAK community support | FastAPI, Django |
| gevent for async I/O | Compatible with Flask, scales well for many concurrent TCP/SSL connections | asyncio / uvicorn |
| RabbitMQ as message broker | Reliable, configured exchanges per message type; decoupling of producers and consumers | Redis Pub/Sub, direct threading |
| PostgreSQL as database | Robust, supports complex queries for CoT data and missions | SQLite (too limited for production), MySQL |
| Internal Certificate Authority | No external dependency for client certificates; required by TAK protocol | Let's Encrypt (not suitable for client certs) |
| MediaMTX for video | Open-source, supports all common streaming protocols | Wowza, Ant Media (commercial) |
| nginx as reverse proxy | Production-grade TLS termination, load balancing, static files | Caddy, Apache |

## 8. Risks

| ID | Description | Impact | Probability | Owner | Mitigation |
|---|---|---|---|---|---|
| R-01 | RabbitMQ single point of failure | High | Low | OTS team | Clustering / monitoring |
| R-02 | Default CA password "atakatak" in production | High | Medium | Operator | Mandatory password change at installation |
| R-03 | Default PostgreSQL credentials in configuration | High | Medium | Operator | Secure config.yml, secrets management |
| R-04 | gevent monkey-patching may conflict with certain libraries | Medium | Low | OTS team | Extensive integration tests |
| R-05 | Federation not yet implemented | Medium | Certain | OTS team | On roadmap; no federated scenarios to be deployed |
