## 1. Purpose

This Technical Design describes the operation of the **CoT message pipeline** in OpenTAKServer: the complete path of an incoming Cursor on Target (CoT) XML message — from TCP receipt via the EUD Handler, through RabbitMQ, to database storage and distribution to other clients.

This is the most critical data path in the system: all location messages, chat messages, CasEvac reports, and situation reports follow this route.

## 4. Prerequisites

- [ ] OpenTAKServer is installed and configured
- [ ] RabbitMQ is running and reachable at `OTS_RABBITMQ_SERVER_ADDRESS`
- [ ] PostgreSQL is running and the database has been migrated (`flask db upgrade`)
- [ ] At least one TAK client is configured with the server address
- [ ] For SSL: client certificate enrolled via the Marti certificate enrollment API
- [ ] Firewall allows ports 8087 (UDP), 8088 (TCP) and/or 8089 (SSL)

## 5. Procedure

### Step 1 — Establish TCP connection

**Action:** TAK client opens a TCP connection:
- Plaintext: `tcp://<serverip>:8088`
- SSL: `ssl://<serverip>:8089` (with client certificate)
- UDP: `<serverip>:8087`

`EudServer` / `EudServerSSL` accepts the connection. An `EudHandler` instance is created per connection.

**Expected Result:** Connection accepted. Log: `New connection from <ip>:<port>`.

**Verification:** Server log (`~/ots/logs/opentakserver.log`); WebUI → EUDs shows the device.

---

### Step 2 — Receive and validate CoT XML

**Action:** TAK client sends CoT XML:

```xml
<event version="2.0" uid="ANDROID-abc123" type="a-f-G-U-C"
  time="2026-05-28T10:00:00Z" start="2026-05-28T10:00:00Z"
  stale="2026-05-28T10:05:00Z" how="m-g">
  <point lat="52.3702" lon="4.8952" hae="5.0" ce="10.0" le="999999.0"/>
  <detail>
    <contact callsign="Alpha-1" endpoint="*:-1:stcp"/>
    <group name="__ANON__" role="Team Member"/>
    <status battery="85"/>
  </detail>
</event>
```

**Expected Result:** Message parsed. Required fields present.

**Verification:** No error message in log.

---

### Step 3 — Publish to RabbitMQ `cot_parser` exchange

**Action:** EudHandler publishes message to `cot_parser` exchange (type: `direct`), persistent (`delivery_mode=2`), TTL 86,400,000 ms.

**Expected Result:** Message present in RabbitMQ queue.

**Verification:** RabbitMQ Management UI (port 15672) → Queues: message present and consumed.

---

### Step 4 — CoT Parser Consumer processes the message

**Action:** Consumer (`OTS_COT_PARSER_PROCESSES`, default 1) processes the message:

1. **Classify** message type on CoT `type` field:
   - `a-*` → Atom (location messages)
   - `b-*` → Bit (chat, files)
   - `t-*` → Tasking (CasEvac, ZMIST)

2. **Store in PostgreSQL**: CoT record with `uid`, `type`, `lat`, `lon`, `hae`, `time`, `stale`, `callsign`. Update EUD record.

3. **Route** to appropriate exchange:
   - Direct messages → `dms`
   - Group messages → `groups` (routing key = group name)
   - Chat messages → `chatrooms`
   - Mission updates → `missions`
   - All → `firehose`
   - WebUI → `flask-socketio`

**Expected Result:** Message stored in DB and published to downstream exchanges.

**Verification:** `SELECT * FROM cot WHERE uid = 'ANDROID-abc123' ORDER BY time DESC LIMIT 1;`

---

### Step 5 — Distribution to receiving clients

**Action:** Consumers on downstream exchanges forward CoT XML:
- **Group clients**: all subscribed EUD handlers receive via TCP/SSL.
- **WebUI**: SocketIO event via `flask-socketio` exchange; live map shows position.
- **Firehose**: logging, monitoring, external integrations.

**Expected Result:** All TAK clients in the same group receive the position update.

**Verification:** Receiving ATAK shows icon; WebUI live map shows icon within 2 seconds.

## 6. Verification and Acceptance Criteria

| Criterion | Verification Method | Acceptance Value |
|---|---|---|
| CoT message received by server | Server log + RabbitMQ queue | Log entry present, queue count +1 |
| Message stored in database | SQL query on `cot` table | Record present with correct lat/lon/time |
| Message visible on WebUI map | Visual inspection of WebUI | Icon appears within 2 seconds |
| Message received by other client | TAK client inspection | Position icon visible on other ATAK |
| SSL connection works with client cert | ATAK SSL connection test | Connection successful, no cert error |
| UDP broadcast functioning | UDP client test | Messages received on port 8087 |

## 7. Rollback Procedure

1. Stop server: `sudo systemctl stop opentakserver`
2. Check RabbitMQ: `sudo systemctl status rabbitmq-server`
3. Check PostgreSQL: `sudo systemctl status postgresql`
4. Check log: `tail -f ~/ots/logs/opentakserver.log`
5. Roll back DB migration: `flask db downgrade` (if applicable)
6. Restart server: `sudo systemctl start opentakserver`
7. Validate: repeat verification steps from section 6

## 8. Known Issues and Workarounds

| Issue | Circumstance | Workaround |
|---|---|---|
| RabbitMQ connection lost under high load | Many concurrent EUDs | Configure `heartbeat` in pika; use connection recovery |
| CoT messages lost on restart | Non-persistent queues | Queues are `durable=True`; messages with `delivery_mode=2` survive restart |
| gevent + pika blocking I/O conflict | Monkey-patching on startup | pika `BlockingConnection` works correctly due to monkey-patching |
| Large CoT backlog with slow consumer | Many messages at once | Increase `OTS_COT_PARSER_PROCESSES` |
| UDP messages not received behind NAT | Client behind NAT router | Use port forwarding or switch to TCP |
