## 1. Doel

Dit Technisch Ontwerp beschrijft de concrete werking van de **CoT-berichtenpijplijn** in OpenTAKServer: het volledige pad van een binnenkomend Cursor on Target (CoT) XML-bericht — van TCP-ontvangst via EUD Handler, door RabbitMQ, naar databaseopslag en distributie aan andere clients.

Dit is het meest kritieke datapad in het systeem: alle locatieberichten, chatberichten, CasEvac-meldingen en situatiemeldingen volgen deze route.

## 5. Procedure

### Stap 1 — TCP-verbinding tot stand brengen

**Actie:** TAK-client opent TCP-verbinding:
- Plaintext: `tcp://<serverip>:8088`
- SSL: `ssl://<serverip>:8089` (met clientcertificaat)
- UDP: `<serverip>:8087`

`EudServer` / `EudServerSSL` accepteert de verbinding. Een `EudHandler` instantie wordt aangemaakt per verbinding.

**Verwacht resultaat:** Verbinding geaccepteerd. Log: `New connection from <ip>:<port>`.

**Verificatie:** Serverlog (`~/ots/logs/opentakserver.log`); WebUI → EUDs toont het apparaat.

---

### Stap 2 — CoT XML ontvangen en valideren

**Actie:** TAK-client verstuurt CoT XML:

```xml
<event version="2.0" uid="ANDROID-abc123" type="a-f-G-U-C"
       time="2026-05-28T10:00:00Z" start="2026-05-28T10:00:00Z"
       stale="2026-05-28T10:05:00Z" how="m-g">
  <point lat="52.3702" lon="4.8952" hae="5.0" ce="10.0" le="999999.0"/>
  <detail>
    <contact callsign="Alpha-1" endpoint="*:-1:stcp"/>
    <group name="__ANON__" role="Team Member"/>
    <status battery="85"/>
  </detail>
</event>
```

**Verwacht resultaat:** Bericht geparseerd. Verplichte velden aanwezig.

**Verificatie:** Geen foutmelding in log.

---

### Stap 3 — Publiceren op RabbitMQ `cot_parser` exchange

**Actie:** EudHandler publiceert bericht op `cot_parser` exchange (type: `direct`), persistent (`delivery_mode=2`), TTL 86.400.000 ms.

**Verwacht resultaat:** Bericht in RabbitMQ queue.

**Verificatie:** RabbitMQ Management UI (poort 15672) → Queues: bericht aanwezig en geconsumeerd.

---

### Stap 4 — CoT Parser Consumer verwerkt het bericht

**Actie:** Consumer (`OTS_COT_PARSER_PROCESSES`, standaard 1) verwerkt het bericht:

1. **Classificeer** berichttype op CoT `type` veld:
   - `a-*` → Atom (locatieberichten)
   - `b-*` → Bit (chat, bestanden)
   - `t-*` → Tasking (CasEvac, ZMIST)

2. **Sla op in PostgreSQL**: CoT-record met `uid`, `type`, `lat`, `lon`, `hae`, `time`, `stale`, `callsign`. EUD-record bijwerken.

3. **Routeer** naar juiste exchange:
   - Directe berichten → `dms`
   - Groepsberichten → `groups` (routing key = groepsnaam)
   - Chatberichten → `chatrooms`
   - Missie-updates → `missions`
   - Alles → `firehose`
   - WebUI → `flask-socketio`

**Verwacht resultaat:** Bericht opgeslagen in DB en gepubliceerd op downstream exchanges.

**Verificatie:** `SELECT * FROM cot WHERE uid = 'ANDROID-abc123' ORDER BY time DESC LIMIT 1;`

---

### Stap 5 — Distributie aan ontvangende clients

**Actie:** Consumers op downstream exchanges sturen CoT XML door:
- **Groepsclients**: alle geabonneerde EUD-handlers ontvangen via TCP/SSL.
- **WebUI**: SocketIO-event via `flask-socketio` exchange; live kaart toont positie.
- **Firehose**: logging, monitoring, externe integraties.

**Verwacht resultaat:** Alle TAK-clients in dezelfde groep ontvangen de positie-update.

**Verificatie:** Ontvangende ATAK toont icoon; WebUI live kaart toont icoon binnen 2 seconden.

## 6. Verificatie en acceptatiecriteria

| Criterium | Verificatiemethode | Acceptatiewaarde |
|---|---|---|
| CoT bericht ontvangen door server | Serverlog + RabbitMQ queue | Log entry aanwezig, queue-count +1 |
| Bericht opgeslagen in database | SQL query op `cot` tabel | Record aanwezig met correcte lat/lon/time |
| Bericht zichtbaar op WebUI kaart | Visuele inspectie WebUI | Icoon verschijnt binnen 2 seconden |
| Bericht ontvangen door andere client | Inspectie TAK-client | Positie-icoon zichtbaar op andere ATAK |
| SSL-verbinding werkt met clientcert | ATAK SSL-connectie test | Verbinding succesvol, geen cert-fout |
| UDP broadcast functioneert | UDP-client test | Berichten ontvangen op poort 8087 |

## 7. Rollback procedure

1. Stop server: `sudo systemctl stop opentakserver`
2. Controleer RabbitMQ: `sudo systemctl status rabbitmq-server`
3. Controleer PostgreSQL: `sudo systemctl status postgresql`
4. Controleer log: `tail -f ~/ots/logs/opentakserver.log`
5. Rollback DB migratie: `flask db downgrade` (indien van toepassing)
6. Herstart server: `sudo systemctl start opentakserver`
7. Valideer: herhaal verificatiestappen sectie 6

## 8. Bekende issues en workarounds

| Issue | Omstandigheid | Workaround |
|---|---|---|
| RabbitMQ verbinding verloren bij hoge load | Veel gelijktijdige EUDs | Configureer `heartbeat` in pika; gebruik connection recovery |
| CoT-berichten verloren bij herstart | Niet-persistente queues | Queues zijn `durable=True`; berichten met `delivery_mode=2` overleven herstart |
| gevent + pika blocking I/O conflict | Monkey-patching bij startup | pika `BlockingConnection` werkt correct dankzij monkey-patching |
| Grote CoT-backlog bij trage consumer | Veel berichten tegelijk | Verhoog `OTS_COT_PARSER_PROCESSES` |
| UDP berichten niet ontvangen achter NAT | Client achter NAT-router | Gebruik port forwarding of schakel over op TCP |
